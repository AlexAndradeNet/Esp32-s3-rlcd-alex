# Bridging Microcontrollers and Microservices: Lessons in Hardware Isolation, Replay Defense, and Code Discipline

## 1. Collaboration & Prompt Constraints

- Function-Level Diffing Beats Full-File Rewrites: Generating entire 1,000+ line firmware sketches repeatedly invites unintended changes (formatting style, bracket placement, comments, or default values). When working under strict code-preservation constraints, providing only the touched functions or diffs prevents accidental modifications and reduces compile risks.
- Separation of Intent vs. "Cleanups": Aesthetic cleanups (such as expanding single-line if statements or adding curly braces) can inadvertently look like arbitrary code tampering. Code formatting and style must be treated as completely frozen unless explicitly requested.

## 2. ESP32 Embedded Systems & Hardware Architecture

- Filesystem-as-State-Machine: Storing the transmission state directly in the filename (_pending.wav \to _OK.wav / _failed.wav) creates an atomic, persistent state machine. This eliminates the need for volatile RAM tracking or auxiliary SQLite/JSON manifests that risk corruption during unexpected battery cuts or brownouts.
- Decoupling File Metadata from Network State: In battery-constrained IoT devices with intermittent Wi-Fi, volatile variables (like current_recording_started_at) cannot be trusted across deferred retries. Encoding timestamps into filenames and parsing them via sscanf preserves the historical capture time without requiring persistent clock tracking.
- Resource Isolation (Heap vs. Stack & Watchdogs): Heavy operations like multi-megabyte SHA-256 calculation and chunked network streaming will trigger silent stack overflows and Task Watchdog Timer (TWDT) panics if large buffers are allocated on the stack. Allocating fixed 2048-byte buffers on the heap (malloc) and introducing non-blocking pauses (delay(10)) prevents SPI bus contention between SD reads and Wi-Fi transmissions.

## 3. Backend & Cryptographic Handshakes

- Idempotency vs. Anti-Replay Alignment:
  - The idempotency key must represent the recording event (<device_id>_<recording_started_at>) to prevent duplicate backend jobs if the device retries.
  - The HMAC anti-replay signature must use the current transmission time (request_timestamp). Binding the signature to the recording start time breaks delayed offline retries because the timestamp falls outside the server’s drift window (e.g., \pm 300\text{s}).
- Explicit Timezone Designators in Web Clients: Standard datetime.isoformat() outputs can omit explicit Z suffixes depending on how UTC is handled. Without strict normalization (appending Z or a UTC offset), browser JavaScript engines may parse the string as local time or fail gracefully into UTC. Explicitly normalizing strings before passing them to new Date() ensures consistent client-side timezone rendering.
